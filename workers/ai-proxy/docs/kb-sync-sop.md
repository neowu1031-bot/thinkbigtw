# 客服知識庫同步 SOP（官網＋LINE AI 客服）

官網 AI 顧問與 LINE 官方帳號 AI 客服共用同一份知識庫。客服要能清楚回答三件事：

1. **官網內容**：每一頁有什麼（方案頁、企業頁、作品集、AI 實戰體驗、Library、問答圖書館的主題範圍、隱私、條款、預約）。
2. **每個方案實際交付什麼**：企業方案、個人方案、年約與加購、SEO＋GEO 服務、問答內容代寫等。
3. **過程用到哪些技術**：硬體、模型、部署方式、文件與權限、資安做法、交付流程、維護。

## 檔案在哪裡

| 檔案 | 用途 |
|---|---|
| `data/agent-kb/01–12*.md` | 核心章節。官網主力路徑每次都整本讀取 |
| `data/agent-kb/13*.md` 起 | 補充章節（官網導覽、隱私與條款、方案交付物、本地大模型技術問答）。依提問命中才載入 |
| `workers/ai-proxy/src/thinkbig.js` | `TOPICS`（每章的檢索正則）、`SCOPE_RULE`（回答範圍與紅線）、`KB_FULL_LIMIT` |
| `scripts/build-agent-kb.mjs` | 由 Markdown 產生 `agent-kb.generated.js` 與 `assets/agent-faq.generated.js`，並檢查 token 預算 |
| `data/agent-kb-eval/questions-60.json` | 60 題驗證題（官網 20、方案交付 20、技術 20，刁難題分散在三類） |
| `scripts/eval-agent-kb.mjs` | 0 token 覆蓋檢查：每題跑 LINE 與官網兩條實際路徑，確認答題依據有送到模型 |

## Token 預算（改內容前先看）

- **LINE（含 LINE 的主力模型）與官網備援路徑**（`selectKnowledge`）：ch01＋ch10 是固定基底，再加命中的章節，總量 ≤ 2850（估算值）。所以**每一章本身不能超過約 1,520**；build 會擋。
- **官網主力路徑**（`selectKnowledgePrimary`）：核心章節 01–12 全文，加上命中的補充章節，總量 ≤ `KB_FULL_LIMIT`（16000）。目前核心約 12,400，所以一次最多再帶 2 章補充；回傳的 `tier` 是 `core` 或 `core+supplement`，`omitted` 列出命中但放不下的章節。
- 個人／企業意圖由 `detectIntent` 判斷，兩條路徑共用：個人意圖時只帶個人相關補充章（13、14、16）；最新一句是技術題（顯示卡、Ollama、RAG…）且沒點名個人方案，就走企業技術章。
- 估算方式：中日韓字 1 字算 2、英數 1 字算 1/3。量某一章：`node scripts/build-agent-kb.mjs` 的輸出，或自己用同一公式算。
- 一章放不下時，**拆成兩章並各自寫 `TOPICS` 正則**，不要調高 2850（最後一層備援模型的上下文很小）。

## 什麼時候要同步

- 官網新增方案、改方案內容、改交付天數或流程。
- 官網大改版、新增重要頁面或專區。
- 交付用的技術組合改變（硬體門檻、模型、部署軟體、資安做法）。
- 問答圖書館或 NEWS 新增新主題類別（單篇文章不用逐篇進知識庫，類別有變才更新 ch13）。

## 步驟

1. **找來源**：先跑 `python3 scripts/build-llms-full.py` 重產 `llms-full.txt`，從裡面找改到的頁面。技術內容只用公司內部文件或官方公開資料，並在章節的 `來源：` 行寫出處（`版本：`、`來源：` 兩種行會在產生時移除，不佔預算）。
2. **改 Markdown**：改對應章節，或新增 `NN-主題.md`（編號接續）。新增章節時，同步在 `thinkbig.js` 的 `TOPICS` 加正則；正則要用具體詞，避免「方案」「多少」這類泛用詞搶走其他章節。個人方案相關的補充章要加進 `PERSONAL_SAFE_SUPPLEMENTS`。
3. **紅線自查**（每次都要）：
   - 不寫任何價格或金額；企業一律「依需求報價」。
   - 不放客戶名稱或可推知身分的案例細節。
   - 不批評、不貶低其他公司。
   - 企業交付時程一律寫「範圍凍結與資料到位後 30 天內」。
   - 不承諾成效、準確率、營收或人力節省。
   - 規格建議一定附前提（人數、文件量、同一時間幾人在問），最後導到預約 30 分鐘免費評估。
   - 禁用字：照公司對外文案紅線清單逐字檢查（否定句也不能用）。
4. **重新產生**：`node scripts/build-agent-kb.mjs`。出現 `Fallback budget exceeded` 就把那一章縮短或拆章。
5. **改 60 題**（題庫在 repo 裡，任何人都能重跑）：方案或頁面有變，就更新 `data/agent-kb-eval/questions-60.json` 裡相關題目的 `must`（答題必須出現的事實，用正則）。新方案至少補 1 題；總題數維持 60，三類各 20。
6. **跑檢查**：
   ```bash
   node scripts/eval-agent-kb.mjs            # 門檻 54/60，兩條路徑都要過
   cd workers/ai-proxy && npm test          # 跑 src/ 底下全部單元測試
   node scripts/build-agent-kb.mjs --check
   ```
7. **模型實答抽查**：覆蓋檢查只證明依據有送到模型。改動較大時，用目前線上模型（或另一個模型模擬）實答 60 題，逐題標 PASS／FAIL：答對、照知識庫不亂補、紅線、台灣用語、該導評估時有導。目標 54 題以上 PASS；FAIL 的回頭補章節或調 `TOPICS`，再跑一次。
8. **對抗審**：請另一個模型或另一位同事專挑毛病（紅線、亂掰的規格、中國用語、對外承諾），改完才送 PR。
9. **送 PR**：這個 repo 是公開的，PR 標題、說明與 commit 訊息就是對外文字，不寫內部人名、客戶資訊或內部金額。CI（`check-generated.yml`）會再跑一次產生檔檢查與 60 題覆蓋檢查。

## 技術內容的口徑（2026-10-31 對齊）

- 硬體、模型、部署方式只寫**目前標準交付組合**（Ubuntu 24.04 原生＋NVIDIA 24GB 以上＋Ollama＋Dify）；一般知識（例如 Mac 也能跑模型、vLLM 是什麼）要和「我們目前受理的範圍」分開寫。
- 不在標準組合的東西（16GB／AMD 顯示卡、Mac、Windows、vLLM、DGX、其他模型）寫「另案評估、以實測為準」，不寫成可直接選的選項。
- 工具的預設值（例如上下文長度、同時處理數）會隨版本改變，不寫具體數字；部署時明確設定並寫進部署附件。
- 廠商資料保存條款（例如 API 資料保存天數）依功能而不同，只寫「依當時條款逐項核對」，不寫概括上限。
