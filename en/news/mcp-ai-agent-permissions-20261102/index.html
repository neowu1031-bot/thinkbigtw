What Is MCP? Set Permission Boundaries Before Connecting an AI Agent

Think BIG Media  |  November 2, 2026

Before connecting an agent, define what it may read, change, and send. Review the connection protocol, authentication, and business approvals separately.

One. What’s Happening: Connections Are Easier; Accountability Stays with the Business

In May 2025, Anthropic announced an API MCP connector that let developers connect to remote MCP servers without writing separate client code.[1] That announcement is the starting point for this practical discussion, rather than a new product update. Easier connections shift the business question from whether an agent can connect to what it may do afterward.

MCP stands for Model Context Protocol. Its tools specification lets servers expose functions a model can invoke, including database queries, API calls, and computations.[3] Reading a list and editing it remain different business actions even when both appear in the same tool menu. We recommend assigning approval conditions to each action.

The authorization document at the 2025-06-18 path covers HTTP transports and says STDIO implementations should obtain credentials from the environment instead.[2] The tools document requires server access controls and recommends user confirmation for sensitive operations.[3] A successful connection therefore does not complete permission acceptance.

Two. Perspectives: Interoperability Helps; Authorization Still Needs Work

The case for adoption: The connector announcement describes less custom client work for remote integrations.[1] In our assessment, a consistent interface can also help teams inventory tools. It does not make each connected system’s data boundaries or business responsibilities identical.

The caution: The authorization specification requires servers to validate that access tokens were issued for them.[2] The security guidance describes how insufficiently restricted local MCP programs can execute commands, expose data, or cause data loss.[4] These are implementation risks, not a claim that every MCP service has suffered an incident.

We recommend separate records for connectivity, permissions, and approvals. Engineering maps the data flow. The system owner defines accessible fields. The business owner identifies changes that require a person to approve them. Being signed in should not serve as permission for every available action.

Consider a hypothetical permission test: someone may read a document, but may they ask the agent to email it externally? If the answers differ, document separate conditions for reading and sending. The approval view should identify the actual document and recipient, with consent scoped to this action.

For cross-system work, map revocation responsibilities. Disabling the AI tool, disconnecting MCP, and revoking a downstream account are different control points; the required combination depends on the architecture. Ask the maintainer to demonstrate shutdown and test the result. Track unfinished work before deciding how to close it.

We also recommend acceptance with a restricted test identity, beyond an administrator’s successful demonstration. Run both permitted and denied actions and have the owner review the reasons. This establishes a usable baseline for future access changes.

◆ First-Hand Lessons

Three. What We Learned in Practice

These points come from our review practice for skills, plugins, and MCP servers. They are not industry statistics or an account of any particular organization.

1. Read what the program actually does. We check its source, maintainer, license, access to environment variables or keys, outbound connections, and execution of downloaded code. A tool labeled “search” still needs a review of its actual operations.

2. Review permissions and versions together. We check requested privileges and pin versions. Packages that fail review are not installed. This creates a traceable decision before introducing third-party code; it does not remove all risk.

3. Record unresolved questions. Extending that practice, we recommend tracking unexplained destinations, write operations, and credential sources. A program starting successfully is not a reason to close the review.

Four. Our Recommendations: Turn Boundaries into Repeatable Tests

1. Inventory tools. Record the system, account, folders or tables, read and write capabilities, and owner. Start query tools with read-only accounts. Document the reason and approver for any write access.

2. Enforce restrictions in the system. Use account permissions, API authorization, or server rules, then test that out-of-scope requests are rejected. Prompts can explain a policy; acceptance should demonstrate its enforcement.[3]

3. Preview sensitive operations. We recommend human confirmation before sending messages, deleting records, or changing production data. Show the recipient, target, and proposed change. This turns the specification’s confirmation guidance into a usable workflow.[3]

4. Test revocation and record results. With test data, check permitted access, denied access, and failure after revocation. Record time, actor, and outcome without logging full credentials. Set tool-call timeouts too.[2][3]

Demonstrate permission boundaries with rejection tests and approval records.

◆ Editor’s Note · How Think BIG Approaches This: Connections You Can Revoke

Deliver the tool inventory, approval conditions, and revocation tests together.

(The following is Think BIG’s practical position, separate from the reporting above.)

Our position is that every integration should have a documented purpose, data scope, and maintenance contact. Human confirmation for sensitive operations belongs in acceptance. Review the changed components whenever a tool or permission is added.

The handover should let the owner understand the authorization and stop the connection.

Frequently Asked Questions

Q1: Is MCP an AI model?
No. Its tools specification describes how models invoke external functions.[3]
Q2: Does MCP handle all permissions?
Access controls still need implementation in the server and connected systems.[2][3]
Q3: Should local MCP programs be reviewed?
Yes. The security guidance identifies local command execution and data access risks.[4]
Q4: What should require approval?
We recommend previews and designated approvers for messages, deletions, and production changes, applying the sensitive-operation guidance.[3]
