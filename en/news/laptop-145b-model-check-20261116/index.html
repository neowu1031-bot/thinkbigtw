A Vendor Says a Laptop Can Run a 145B Model. Can Yours? Total Parameters, Active Parameters, and Measured Memory Are Three Different Numbers

Think BIG Media  |  November 16, 2026

The "145B," "about 10B," and "29GB" in one announcement measure three different things: how big the model is in total, how much is computed at each step, and the most memory used under the vendor's own test setup. When you see specs like these, ask which machine and which conditions each number came from, then test on your own machine and your own documents.

(Every vendor figure in this article comes from the company's own announcement and is vendor-reported. We have not reproduced any of it. This article does not rate the company or the model, and it takes no position on whether the model performs as described.)

One.What's Happening: Three Numbers in One Announcement

On November 12, 2026, Edge0 released two open-weight models, Edge0-145B and Edge0-120B, together with an inference framework and deployment tools.[1] For the 145B model, the post gives several figures at once (all vendor-reported):

Total parameters: 145B.

Active parameters: roughly 10B take part in computation at each inference step.

Peak memory: 29GB.

Tiered storage: an expert library of about 40GB sits in system memory, and about 48GB of vocabulary data sits on the SSD and is read on demand.

Speed and context: decoding at 80+ tokens per second, prefill at 1,100+ tokens per second, and a 128K–256K context. The post also lists about 120W typical power and says there was no throttling in its reported setup.[1]

The three numbers most often mixed up answer different questions:

Total parameters: 145B: measures how many parameters the model has in all. The question it answers: how large the weights are and where they have to live.

Active parameters: about 10B: measures parameters used in computation at each step. The question it answers: how much work each step does; it relates to speed and does not mean only this much has to be loaded.

Peak memory: 29GB: measures the most memory used under the vendor's reported test setup. The question it answers: usage under that setup, not whether your machine is enough.

That breakdown is our reading. The post's own description is that weights are spread across GPU memory, system memory, and SSD, with reading and computation overlapping.[1]

What the post does not say, and the limits it does state:

Which machine produced the 29GB figure: the post says only "a compatible laptop, such as a MacBook Pro," with no chip or memory configuration.

What context length the 29GB was measured at: not stated.

Whether the 40GB and 48GB figures add to the 29GB: the post gives no calculation.

The full evaluation setup, hardware environment, and reproduction steps: the post says they will come with a technical report.[1]

The post itself cautions that this does not mean every device can run the 145B model; very low-compute devices need a smaller model or the cloud, and cross-device long-term memory and searches that need current information still need cloud services.[1]

License: the post says open source and points to Hugging Face for the weights. The body text does not name a license.[1]

Two.The Case for Specs, and the Case for Acceptance Tests

The case for reading the specs: the post handles "will it fit" by splitting storage into three tiers, and it mentions use on a laptop with 48GB of memory.[1] For teams that want to run large models locally, that means "fits" is no longer a single number, and the architecture description deserves a careful read.

The case for acceptance testing: Ollama's documentation says a longer context length raises the memory a model needs, that you should confirm you have enough VRAM before raising it, and that for best performance you should avoid offloading to the CPU. The ollama ps PROCESSOR column shows the split.[2] The NIST AI Risk Management Framework (AI RMF 1.0), under MEASURE 2.3, says performance should be demonstrated under conditions similar to the deployment setting, with the measurements documented.[3]

The two views can coexist. The order is what matters: the vendor's specs help you decide whether a model belongs on the shortlist, and testing on your own machine decides whether you can tell a user "yes."

◆ First-Hand Lessons

Three. What We Learned in Practice

These are the habits we follow when we evaluate local models. They are not industry statistics and do not describe any particular client.

1. If we haven't tested on a machine in the same class as the client's, we don't tell the client it will work. The memory figure on a spec sheet often differs from what you see during long use. The gap usually comes from context length, other programs running at the same time, and the class of the machine.

2. "It runs" and "it's usable" are different things. A model can load and answer its first prompt, and still slow down after hours of continuous use. Time to first token and slowdown over long sessions need to be measured separately.

3. We label vendor numbers "vendor-reported," every time. That is not distrust. It tells whoever retests later where the number came from and which conditions were never stated.

Four.Our Recommendations: A Three-Step Acceptance Check

1. Check the license and where the weights come from. Confirm where the weights are downloaded from and read the license text itself, including what it says about commercial use, redistribution, and modification. "Open source" in an announcement is not enough.

2. Test on the target machine. Use the context length you will actually use, with the programs you normally keep open, and measure three things: peak memory, time to first token, and slowdown after long use. Record the machine model, memory size, context length, and test duration.[2][3]

3. Treat vendor benchmarks as leads, and check with a small sample of your own documents. Public benchmarks test someone else's questions. Take ten to twenty documents or questions you really handle, run them through, and have the person who owns that work review the results.

In one sentence: the spec sheet tells you a model is worth trying; your machine and your documents tell you whether it works.

◆ Editor’s Note · How Think BIG Approaches This

Leave a Record That Can Be Retested

(The following is Think BIG's practical position, separate from the reporting above.)

When we evaluate a local model for a company, we deliver more than "it's installed." A few examples:

Machine test record: peak memory, time to first token, and slowdown over continuous use, measured on a machine in the same class as yours and delivered with the test conditions.

Document acceptance set: questions and results built from a small sample of your own documents, so a later model change can be retested against the same set.

License and source record: where the weights came from and how to read the license, summarized on one page.

These are just a few of the things we do. Other workflows can be customized to your needs.

Frequently Asked Questions

Q1: Does 145B mean I need enough memory to hold 145 billion parameters?
You can't conclude that from this number alone. The post says about 10B parameters take part in each step and that weights are spread across GPU memory, system memory, and SSD.[1] What you actually need depends on your machine and settings, so test it.
Q2: The post says 29GB. Is my 32GB laptop enough?
You can't infer that directly. The post doesn't say which machine or context length produced 29GB, and it mentions use on a laptop with 48GB of memory. It also describes model weights as competing with the operating system and other apps for limited memory and bandwidth.[1] Go by a test on your own machine.
Q3: Can I treat the vendor-reported speed as what I'll get?
Treat it as a lead. The post says the full evaluation setup and hardware environment will be released with a technical report.[1] NIST's guidance is to measure under conditions similar to deployment and to document the results.[3]
Q4: The announcement doesn't name a license. What should I do?
The post says open source and points to Hugging Face for the weights, but it names no license.[1] Before adoption, read the license text on the model page and confirm the limits on commercial use, redistribution, and modification.
Q5: How can I tell whether a model is fully loaded into video memory?
With Ollama, run ollama ps and read the PROCESSOR column. "100% GPU" means the model is fully loaded on the GPU, and a CPU percentage means part of it sits in system memory.[2] For other tools, check their own documentation for the equivalent.
