An AI Agent Ran All Night? — Set Limits, Schedules, and Stop Conditions

Think BIG Media  |  November 22, 2026

Start with schedules and retries. Usage alerts, blocking new work, and canceling work already underway are separate controls that need separate tests.

One.Agent Loops Accumulate Resource Use

An agent may call a model repeatedly for one task. In its June 13, 2025 research-system report, Anthropic describes agents exploring directions in parallel and warns that this architecture consumes tokens rapidly. Those observations belong to that system, not to every business deployment.[1]

OWASP’s 2025 LLM10 entry treats uncontrolled inference consumption as a risk and recommends input limits, rate limits, quotas, timeouts, and monitoring.[2] A task still running deserves a check on its progress and stopping conditions.

Controls also differ by layer. Pydantic AI distinguishes model turns from successful tool executions; a turn count does not cover every underlying transport attempt.[3] AWS warns that a timeout does not establish that a remote action failed to happen, and retries can add load to an overloaded service.[4]

Two.Room to Explore Needs a Boundary

The case for execution room: exploration takes work. The research report describes tasks whose direction changes as evidence arrives.[1] Our reading is that forcing every task into a very short run can conflict with the work. Limits should reflect the task.

The caution: distinguish progress from repetition. OWASP recommends resource monitoring as well as input controls.[2] We suggest tracking completed steps, repeated actions, and stop reasons. Token totals alone do not measure quality, and an unfinished answer does not justify an open-ended run.

More retries do not automatically produce a more reliable service. AWS explains backoff and jitter, while emphasizing the need to consider safe repetition for actions with side effects.[4] We recommend different retry rules for reads and external writes, plus a recoverable state when work stops.

◆ First-Hand Lessons

Three. What We Learned in Practice

These observations come from our always-on agent maintenance notes. They are not industry statistics or an account of any particular client.

1. No chat messages does not mean no model calls. Heartbeat checks and automatic memory maintenance can continue consuming quota or compute unnoticed. Our inventory includes background work as well as chat activity. This does not imply that every framework has identical defaults.

2. Inventory, disable, then limit. We list automatic jobs, turn off unnecessary ones, and apply limits. We do not have a universal threshold or a savings percentage, so we make neither claim.

3. Ask who takes over. Our proposed adoption checklist asks for each job’s purpose, trigger, and owner. Agree in advance whether a stopped task waits for review, restarts later, or ends. This is a recommended control, not an additional deployment anecdote.

Four.Our Recommendations: Limits and What Happens Next

1. Inventory triggers. Include timers, incoming events, health checks, and retry queues. Record model calls and external writes. Disable jobs without a clear purpose, then test necessary work.

2. Set several kinds of limits. Manage model turns, tool executions, elapsed time, input and output, and concurrency separately. Check the framework’s definitions rather than treating a turn limit as a count of all network attempts.[2][3]

3. Bound retries and add waiting. Set retry counts, backoff, and an execution deadline. Check the earlier result before repeating an action with side effects. A timeout alone does not mean nothing happened.[4]

4. Test stops and notifications. Deliberately reach a limit. Check whether new work stops, how in-flight work is handled, and who is notified. Include a task identifier, the last completed step, and actions still requiring confirmation.

5. Review background usage. Compare schedules with purpose and look for duplicate triggers or persistent failures. Assign approval and a reason for limit changes instead of expanding the allowance whenever a task fails.[2]

We suggest testing limits with a deliberately failing job: make a test dependency unavailable, verify that retries end as designed, and check that later schedules do not recreate the same work. Also run a successful job to confirm the limits allow normal operation. Retain both records so maintainers can distinguish an intentional stop from a new fault. For shared resources, test what happens to other authorized work when one job reaches its limit, rather than testing a single conversation alone.

◆ Editor’s Note · How Think BIG Approaches This: Make Automated Work Easy to Hand Off

Every scheduled job needs an owner and a purpose.

(The following is Think BIG’s practical position, separate from the reporting above.)

Think BIG’s position is to include schedules, limit scope, stopping procedures, and handoff owners in the operating documentation. A stopping rule belongs in the task design.

Automated work should be inspectable, pausable, and traceable. When work exceeds expectations, preserve progress and unresolved actions so the owner can decide what happens next.

Frequently Asked Questions

Q1: Why is there usage when nobody is chatting?
Our maintenance notes include model calls from heartbeat and memory jobs. Inventory automatic schedules.
Q2: Is a model-turn limit sufficient?
No. Frameworks can count turns and tool executions separately, and transport retries may fall outside the turn count.[3]
Q3: Can I retry immediately after a timeout?
Check the previous outcome first. A remote action with side effects may already have happened.[4]
Q4: Does a usage alert mean the task stopped?
Do not assume so. We recommend testing new-work blocking, in-flight work, and the handoff separately.
