What Should You Back Up in a Local AI System? — Beyond Model Files

Think BIG Media  |  November 20, 2026

Recovering a model does not reconstruct the working system. A backup plan needs file locations, a consistent recovery point, and work-based acceptance checks.

One.A File Copy Is Not a Recovery Plan

Model files are conspicuous, but size should not determine backup priority. Ollama’s FAQ describes configurable model storage and service settings managed through the operating system. The default directory may not describe the deployed setup.[1]

Databases also need specific handling. PostgreSQL says a direct file-level copy requires shutdown; an appropriate consistent snapshot can work while running, provided its conditions, logs, and full data scope are covered.[2]

SQLite offers an online backup API for database snapshots and discusses the locking and interruption risks of traditional copying.[3] CISA recommends offline, encrypted backups of critical data and regular availability and integrity tests.[4] These sources focus on recoverability, beyond simply having another copy.

Two.Offline and Online Methods Have Conditions

The case for stopping writes: a clearer state. Where maintenance windows are possible, we favor stopping writing services before a documented backup. This is our operational choice. PostgreSQL’s restrictions on direct copying do not mean every database requires an offline backup.[2]

The case for online backup: service continuity. SQLite’s API and PostgreSQL’s consistent-snapshot guidance offer conditional paths for working systems.[2][3] Our reading is that database and storage architecture should determine the method. A completed copy command is insufficient evidence by itself.

Convenience also needs to be weighed against isolation. CISA notes that ransomware can delete or encrypt accessible backups.[4] We recommend reviewing backup access separately from everyday access while ensuring an authorized recovery owner can obtain what is needed.

◆ First-Hand Lessons

Three. What We Learned in Practice

These notes come from our local AI deployment and maintenance records. They are not industry statistics or an account of any particular client.

1. The model is one component. Our checklist includes configuration, schedules, service definitions, database snapshots, knowledge indexes, agent memory files, and conversation records. Where model files can be downloaded again, we still record the exact version rather than an ambiguous name.

2. Make a consistent backup before upgrades. Our recorded practice is to stop services before packaging the system, giving the backup a defined point with writes stopped. That is our method, not a universal prescription. Online requirements need a method appropriate to the database.[2][3]

3. Use the existing backup process. We use the established daily backup mechanism rather than adding a separate process without an owner. We consider the job complete after a recovery drill.

Four.Our Recommendations: From Inventory to Recovery

1. Inventory by purpose. Mark what must be preserved and what can be rebuilt. Record locations, owners, versions, retention, and rebuild instructions. If an index will be rebuilt, keep its source documents and build procedure.

2. Document consistency. Identify the services to stop, database order, and how to confirm writing has stopped. For online methods, save options and completion evidence. Do not assume that a copy of a live data directory is a usable snapshot.[2][3]

3. Protect and isolate backups. Consider offline storage and encryption under CISA’s guidance, and test authorized access to recovery and decryption material.[4] Keep secret retrieval controlled rather than placing complete secrets in general handover notes.

4. Restore in isolation. Select a backup, record the steps, and use known questions to check retrieval, memory access, and service startup. Disable outbound scheduled actions during the drill to avoid repeating production work. This is our recommended test design.

5. Return results to the owner. Keep the recovery point, elapsed time, failures, and corrections. Add missing settings to the inventory. Use the revised procedure for the next drill instead of carrying forward an old completion check.

A useful drill can start with one concrete task, such as retrieving a known document. Define the expected answer and authorized account, restore from the instructions, and check the source data, version, and permissions. If an index is rebuilt, confirm that all required originals exist. Compare the drill against the inventory: any file obtained ad hoc during recovery belongs on the next checklist. This is our proposed acceptance method; service startup alone does not establish complete recovery.

Frequently Asked Questions

Q1: Is backing up model files enough?
Our inventory also covers settings, schedules, databases, indexes, memory, and records. Model locations can be customized.[1]
Q2: Can I copy database files directly?
Use a method appropriate to the database. PostgreSQL requires shutdown for a direct file backup; SQLite offers an online backup API.[2][3]
Q3: Do daily backups still need a recovery drill?
Yes. CISA recommends testing availability and integrity regularly.[4]
Q4: Must every model file be duplicated?
We first assess whether it can be obtained again and record the exact version. An uncertain rebuild path should not be treated as disposable.
