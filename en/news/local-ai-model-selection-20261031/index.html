Choosing a Local AI Model: Bigger Isn’t Automatically Better — Test It on Your Own Work

Think BIG Media  |  October 31, 2026

When choosing a local model, ask what work the machine has to do, then whether the model fits, and finally test it on your real tasks. A large model that doesn’t fit in VRAM can run slower than a smaller one that sits entirely on the GPU.

(We use the open-source tool Ollama to illustrate the checks. This article does not rank or recommend any specific model.)
Our Issue 2 asked whether the GPU was doing anything; Issue 11 looked at context lengths set too high. This issue connects the two: the model, the context, and the number of people served at once all draw on the same memory.

One.What’s Happening: The Model and the Context Compete for Memory

"Can I run the biggest one on my own machine?" is often the first question. Answering it means doing the memory math for everything at once.

Ollama's documentation says a larger context length increases the memory needed to run a model, and that you should confirm you have enough VRAM before raising it. The same page recommends at least 64,000 tokens of context for tasks such as agents and coding tools, and advises avoiding offloading the model to the CPU for best performance.[2] The FAQ adds that when serving several requests at once, required memory scales with parallel requests multiplied by context length.[1]

Put simply, an AI agent already needs a fairly large context. The bigger the model you pick, the less room is left for that context and for concurrent requests.

Quantization is the usual trade-off tool. The documentation describes it as storing model weights at lower precision to reduce the memory needed to load and use a model while preserving as much accuracy as possible. Weights are typically stored as 32-bit or 16-bit floating point, and some methods go further down to integer formats such as int8 or int4.[4]

Two.Perspectives: Read the Spec Sheet, or Run the Test?

The spec-sheet view: more parameters and longer context mean more potential. For complex reasoning or very long documents that has merit, and the guidance above does support larger contexts for agent tasks.[2]

The testing view: The US National Institute of Standards and Technology's AI Risk Management Framework (AI RMF 1.0) says accuracy measurements should be paired with clearly defined, realistic test sets that represent conditions of expected use, along with details of the test method; system performance should be measured and demonstrated under conditions similar to the deployment setting.[5] Ollama's FAQ makes a related point about K/V cache quantization: its effect on answer quality depends on the model and task, and you may need to experiment to find the right balance.[1]

Both views can coexist. Order is what matters: the spec sheet decides which candidates are on the list; testing decides which one you pick.

◆ First-Hand Lessons

Three. What We've Learned in Practice

These observations come from our local AI agent deployments. They are not industry statistics and don't describe any particular client.

1. "Which model should we install?" is one of the most common questions, and it has no single answer. The first question is what the machine will mainly do. Answering support emails, summarizing meetings, searching internal documents, and writing code each place different demands on speed, context length, and answer quality.

2. A common sticking point is "it installs, but it can't keep up." The model loads and answers in chat, but slows down on real work or stalls once two or three people use it at the same time. The cause is often a model that's too large: add the context an agent needs, and memory can't hold it all, so part of the model lands on the CPU. The PROCESSOR column in ollama ps shows it at a glance.[1]

3. A size down is often enough. We start with the smallest candidate that passes acceptance, and keep larger models in reserve until real work shows they're needed.

4. Acceptance uses the client's own questions. Public leaderboards test other people's questions. We ask the owner to prepare a set of questions they actually ask, with reference answers, and compare candidates on that.

Four.Our Recommendations: Four Steps

1. Write down the tasks and metrics. List the three to five jobs the machine will do and, for each, the metrics that matter: how many seconds people can wait, how accurate answers must be, whether data can leave the company, and how many people use it at once.

2. Do the memory math: model + context + concurrency. Check whether the model itself fits in VRAM, then add the context and concurrency the work needs.[1][2] Drop candidates that don't fit, or look at quantized versions.[4]

3. Test on your own questions. Prepare questions and reference answers that reflect real use, and record how you tested.[5] For speed, the Ollama API response includes eval_count (output tokens) and eval_duration (time spent generating output, in nanoseconds); divide one by the other for tokens per second.[3] Check ollama ps at the same time to confirm PROCESSOR reads 100% GPU.[1]

4. Pick the smallest model that passes. Among candidates that meet both quality and speed thresholds, choose the smallest. When the work changes, rerun the same test set.

In short: choose a model by measuring it against your work, not by picking the biggest number on the spec sheet.

◆ Editor’s Note · How Think BIG Approaches This: Selections You Can Retest

Task and metric sheet, acceptance test set, runtime evidence — delivered together.

(The following is Think BIG's own practice, kept separate from the reporting above.)

When we help choose a local model, the deliverable is more than an installed model: a task and metric sheet — what each job needs and its thresholds, confirmed by the owner; an acceptance test set — the client's own questions and reference answers, delivered with the test method, so any future model change can be retested the same way; runtime evidence — the PROCESSOR and CONTEXT columns from ollama ps plus speed records, as the basis for handover.

Our position: a model choice should be retestable with the same question set.

Frequently Asked Questions

Q1: Is a model with more parameters always better?
Not necessarily. The model, the context length, and concurrent requests all take memory.[1][2] When a model doesn't fit in VRAM, part of it runs on the CPU and speed can drop noticeably. Test on your own work before deciding.
Q2: How do I know whether a model is running fully on the GPU?
Run ollama ps. PROCESSOR showing 100% GPU means the model is fully loaded on the GPU; 100% CPU or a CPU/GPU split means all or part of it is in system memory.[1]
Q3: Does quantization make a model worse?
Quantization stores weights at lower precision to save memory while trying to preserve accuracy.[4] The actual effect depends on the model and task, and Ollama's documentation suggests experimenting to find the balance.[1] Compare before and after on your own acceptance questions.
Q4: How do I measure a local model's speed?
Ollama's API response includes eval_count and eval_duration (in nanoseconds); divide them to get tokens generated per second. load_duration shows how long the model took to load.[3]
Q5: How should we prepare test questions?
NIST's AI RMF recommends clearly defined, realistic test sets that represent conditions of expected use, with the test method documented.[5] In practice, ask the owner for the questions they really ask, with reference answers.
Q6: How much context does an AI agent need?
Ollama recommends at least 64,000 tokens for agent tasks.[2] That takes a fair amount of memory, so include it when choosing a model; see our Issue 11 for how to set it.
