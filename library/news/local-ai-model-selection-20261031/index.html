本地大模型 · 模型選型 · 顯示記憶體管理

本地 AI 模型怎麼選？參數量不是越大越好——用自己的工作實測再決定

Think BIG 自媒體部  |  2026 年 10 月 31 日

選本地模型，先問「這台機器要做什麼工作」，再問「放不放得下」，最後拿自己的真實工作測。放不進顯示記憶體的大模型，可能比小一號、完整跑在顯卡上的模型更慢。

（本文以開源工具 Ollama 為例說明檢查方式；不評比、不推薦任何特定模型。）
本報第 2 期談「GPU 有沒有在動」，第 11 期談「上下文長度設太大」。這期把兩件事接起來：模型本身、上下文、同時服務的人數，其實都在搶同一塊記憶體。

一現象：模型和上下文搶同一塊記憶體

「能不能在自己的機器上跑參數最大的那個？」是常見的第一個問題。要回答它，記憶體的帳得一起算。

Ollama 官方文件說，上下文長度設大會增加執行模型所需的記憶體，調大前要確認顯示記憶體夠用；同一頁也建議，AI Agent、程式工具這類任務的上下文至少設到 64000 個 token，並為了效能避免模型被卸載到 CPU。[2] FAQ 另外寫明，同時處理多個請求時，所需記憶體會隨「並行請求數 × 上下文長度」放大。[1]

換句話說，要跑 AI Agent，上下文本來就需要開得比較大；模型選得越大，留給上下文和並行請求的空間就越少。

量化是常見的取捨工具。技術文件的說明是：量化把模型權重存成較低精度，以降低載入與使用模型所需的記憶體，同時盡量保留準確度；權重通常以 32 位元或 16 位元浮點數儲存，部分方法可以再降到 int8、int4 這類整數格式。[4]

二各方評價：看規格，還是看實測？

看規格的思路：參數多、上下文長，代表模型潛力大。對需要複雜推理或很長文件的工作，這個方向有它的道理，前面提到的官方建議也支持 Agent 類任務開大上下文。[2]

看實測的思路：美國國家標準暨技術研究院（NIST）的《AI 風險管理框架》（AI RMF 1.0）寫到，準確度的量測應搭配定義清楚、貼近實際使用情境的測試集，並記錄測試方法；系統的效能也應在接近部署環境的條件下量測與呈現。[5] Ollama 的 FAQ 談到 K/V cache 量化時也說，量化對回答品質的影響依模型和任務而定，需要自己實驗找平衡。[1]

兩種思路可以並存，順序比較重要：規格決定「有哪些候選」，實測決定「選哪一個」。

◆ 第一手心得

三、我們實際做的時候的心得

以下是我們部署本地 AI Agent 時的觀察，不是產業統計，也不代表任何特定客戶。

1. 「應該裝哪個模型？」是最常見的問題之一，但它沒有單一答案。要先問的是：這台機器主要做什麼？回客服信、整理會議紀錄、查內部文件、寫程式，對回應速度、上下文長度、回答品質的要求都不一樣。

2. 常見的卡關點是「裝得起來，用不下去」。模型載入成功，對話也答得出來，但一上真實工作就慢，或同時兩三個人用就卡。查下去常常是模型太大，加上 Agent 需要的上下文，記憶體已經放不下，部分跑到 CPU。ollama ps 的 PROCESSOR 欄一看就知道。[1]

3. 小一號的模型常常就夠用。我們的做法是從候選裡最小、能過驗收的那個開始用。比較大的模型留著備用，等真實工作證明需要時再升級。

4. 驗收用客戶自己的題目。公開排行榜測的是別人的題目。我們會請負責人準備一組他們真正會問的問題和標準答案，拿來比較候選模型。

四我們的建議：四步選型

1. 先寫下工作與指標。列出這台機器要做的三到五種工作，每種寫下在意的指標：可以等幾秒、回答要多準、資料能不能離開公司、同時幾個人用。

2. 算記憶體：模型＋上下文＋並行數。先確認模型本身放不放得進顯示記憶體，再加上工作需要的上下文與並行數。[1][2] 放不下的候選先刪掉，或改看量化版本。[4]

3. 用自己的題目測。準備一組貼近真實使用的題目與標準答案，記錄測試方式。[5] 速度可以直接看 Ollama API 回應裡的 eval_count（輸出 token 數）和 eval_duration（產生輸出的時間，單位奈秒），相除就是每秒產生的 token 數。[3] 同時看 ollama ps，確認 PROCESSOR 是 100% GPU。[1]

4. 選最小、能過關的那一個。品質、速度都達標的候選中，挑最小的。之後工作內容變了，再用同一組題目重測。

一句話：選模型是用工作去量，不是看參數表挑最大的。

◆ 編按 · Think BIG 的做法：選型要能重測

任務指標表、驗收題組、執行證據——交付時一起給。

（以下是 Think BIG 的實作主張，與上方報導區隔。）

我們幫人選本地模型時，交付的不只是「裝好的模型」：任務與指標表——每種工作在意什麼、門檻多少，由負責人確認；驗收題組——用客戶自己的問題與標準答案，連同測試方式一起交付，之後換模型可以照同一組重測；執行證據——ollama ps 的 PROCESSOR、CONTEXT 欄位與速度紀錄，作為交付時的依據。

我們的立場是：選型結果要能拿同一組題目重測。

常見問題

Q1：參數量越大的模型越好嗎？
不一定。模型本身、上下文長度與並行請求都要佔記憶體。[1][2] 放不進顯示記憶體時，模型會部分跑到 CPU，速度可能明顯變慢。建議用自己的工作實測再決定。
Q2：怎麼知道模型有沒有完整跑在顯卡上？
執行 ollama ps，PROCESSOR 欄顯示 100% GPU 代表完整載入顯卡；顯示 100% CPU 或 CPU/GPU 比例，代表全部或部分放在系統記憶體。[1]
Q3：量化會讓模型變笨嗎？
量化用較低精度儲存權重來省記憶體，同時盡量保留準確度。[4] 實際影響依模型與任務而定，Ollama 文件也建議自己實驗找平衡。[1] 請用你的驗收題組比較量化前後。
Q4：怎麼量本地模型的速度？
Ollama API 回應附有 eval_count 與 eval_duration（奈秒），兩者相除可算出每秒產生的 token 數；load_duration 可看模型載入花了多久。[3]
Q5：測試題目要怎麼準備？
NIST AI RMF 建議用定義清楚、貼近實際使用情境的測試集，並記錄測試方法。[5] 實務上，請負責人準備他們真正會問的問題與標準答案。
Q6：AI Agent 的上下文要開多大？
Ollama 建議 Agent 類任務至少 64000 個 token。[2] 這會吃掉不少記憶體，所以選模型時要把上下文一起算進去；設定方式可參考本報第 11 期。
