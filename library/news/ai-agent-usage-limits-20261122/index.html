AI Agent · 用量上限 · 排程管理

AI Agent 跑了一整晚沒停？——排程、用量上限與停止條件要一起設

Think BIG 自媒體部  |  2026 年 11 月 22 日

先查誰在排程、誰在重試，再決定上限。用量通知、停止新工作與取消已開始的動作，是三件需要分別驗證的事。

一現象：工作被拆成迴圈，資源也跟著累積

一個問題交給 AI Agent 後，未必只呼叫模型一次。Anthropic 在 2025 年 6 月 13 日公開的研究系統實作文章，說明多個 Agent 可以平行探索不同方向，同時提醒這類架構會快速消耗 token。這是該團隊的實作報告，不能當成所有企業的用量統計。[1]

OWASP《生成式 AI 應用風險》2025 年版的 LLM10，把不受控的推論消耗列為風險，並提出輸入限制、請求速率、配額、逾時與監控等措施。[2] 所以「還在執行」不等於「仍在產生有用結果」，也值得問是否已有停止條件。

技術上也要分層。Pydantic AI 官方文件區分模型回合限制與成功工具執行次數限制；前者不等於每一筆底層傳輸請求。[3] AWS 的重試文件則提醒，逾時不代表遠端動作沒有發生，重試還可能增加原本已過載服務的負擔。[4]

二各方評價：有空間探索，也要有停止界線

支持較大執行空間的理由：有些工作需要探索。上述多 Agent 報告描述的研究任務，需要隨中間結果改變方向。[1] 我們的判讀是，把所有工作都壓到很短的單次回合，可能不符合任務本身；限制應依工作種類設計。

保留的理由：有用的探索與空轉要能分辨。OWASP 建議觀察資源分配與異常用量，而不只限制單一輸入。[2] 我們因此建議，同時看完成項目、重複步驟與停止原因；不能只以總 token 多少判斷品質，也不能因為回答尚未完成就無限放行。

重試也不是越多越穩。AWS 說明退避與隨機延遲可用來分散請求，但有副作用的操作還須考慮能否安全重做。[4] 我們的立場是，對外寫入與單純查詢要有不同的重試規則，停止後也要留下可接手的狀態。

◆ 第一手心得

三、我們實際做的時候的心得

以下來自我們常駐型 AI Agent 的維運紀錄，不是產業統計，也不代表任何特定客戶。

1. 沒人傳訊息，仍然會呼叫模型。心跳檢查、自動整理記憶等排程，會在沒人注意時持續使用額度或運算資源。盤點不能只問誰在聊天，還要逐項看背景工作。這是我們記錄到的現象，不是宣稱所有框架都有相同預設。

2. 先列清單，再關閉不需要的項目。我們會逐項列出自動排程、關掉用不到的、設定上限。我們沒有一套通用的上限數字，也不估算節省比例。

3. 接下來要問誰能接手。在導入檢查清單中，我們會要求說明每項工作的目的、觸發來源與負責人；被停止的任務是等待人工、稍後重跑，還是直接結束，也要事先約定。這是我們提出的檢查方式。

四我們的建議：設好上限，也寫好停下來之後

1. 盤點觸發來源。列出時間排程、訊息事件、健康檢查與重試佇列，記下是否呼叫模型、是否寫入外部系統。先停掉沒有明確用途的工作，再測試必要的工作是否仍能完成。

2. 按任務設多種上限。分別管理模型回合、工具執行、總時間、輸入輸出與並行工作。對照所用框架的計數定義，別把回合上限誤讀為所有網路呼叫的總數。[2][3]

3. 限制重試並留出等待。設定重試次數、退避與最晚結束時間；對有副作用的操作，先確認前次結果再決定能否重送。逾時後不要直接假設「沒有執行」。[4]

4. 測試停止與通知。刻意觸發上限，檢查是否停止新增任務、如何處理已送出的工作，以及誰收到通知。通知文字應包括任務編號、最後完成步驟與待確認動作，方便人工接續。

5. 定期檢查背景用量。以工作目的對照排程紀錄，尋找重複觸發與持續失敗的項目。上限調整要有人核准並記下理由，避免每次任務失敗都只是把限制放大。[2]

建議用一個刻意失敗的測試工作驗收限制：讓外部測試服務暫時無法回應，觀察重試是否按規則結束，並確認後續排程不會再建立相同工作。接著用成功工作確認正常流程沒有被限制擋住。這兩份紀錄一起交給維護人員，才容易判斷日後的停止究竟是預期控制，還是新故障。若多項工作共用資源，也應確認一項任務達到限制時，其他已獲授權的工作如何處理；別只測單一對話。

◆ 編按 · Think BIG 的做法：讓自動工作可以交接

每一項排程，都要有人知道它為何存在。

（以下是 Think BIG 的實作主張，與上方報導區隔。）

Think BIG 主張，常駐 AI Agent 的交接文件應包含排程清單、限制範圍、停止方式與接手人。把「何時停」寫清楚，是任務設計的一部分。

我們希望自動工作能被檢視、暫停與追查。當任務超出預期，先留下目前進度與待確認事項，再由負責人決定下一步；不能讓停止原因消失在背景紀錄裡。

常見問題

Q1：沒有人聊天，為什麼還有用量？
我們維運時看到，心跳檢查與記憶整理也會呼叫模型；應逐項盤點自動排程。
Q2：只限制模型回合就夠嗎？
不夠。框架可能分別計算回合與工具執行，也不一定把底層傳輸重試算進回合。[3]
Q3：逾時後可以直接重送嗎？
先確認前次動作狀態。有副作用的遠端操作，逾時不表示沒有發生。[4]
Q4：用量通知等於停止了嗎？
不能直接畫上等號。我們建議另外測試停止新工作、處理已開始的工作與人工接手流程。
